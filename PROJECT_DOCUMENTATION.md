# Project documentation

Technical write-up of the Retail Bank Cross-Sell and Customer Journey Analytics pipeline. The
README is the overview; this document explains how each part works, why it was built that way, and
what the first full run on the real data showed. All results are quoted from files in `reports/`
(generated by `python -m xsell all` and committed); metric definitions are in
[docs/metric_definitions.md](docs/metric_definitions.md).

## 1. Data

Kaggle competition "Santander Product Recommendation" (2016), file `train_ver2.csv.zip`. Each row is
one customer in one monthly snapshot, with 24 customer attributes (Spanish column names) and 24
product flags. Verified on the first run (`data/cache/manifest.json`, `reports/data_quality.md`):

| Fact | Value |
|---|---|
| Zip size | 224,672,878 bytes |
| Rows | 13,647,309 |
| Customers | 956,645 |
| Snapshots | 17, from 2015-01-28 to 2016-05-28 |
| Customers present in May 2016 | 931,453 |

Quirks handled in staging (`sql/staging/00_stg_holdings.sql`, documented in
[docs/data_dictionary.md](docs/data_dictionary.md)): numbers stored as padded text, the `-999999`
seniority sentinel, `indrel_1mes` spelled `1`, `1.0`, `P` and so on, incomes written as text such
as `NA`, NULL product flags in the two payroll-related columns, missing join dates, and customers
who skip months. The data has no revenue fields.

## 2. Architecture

A batch pipeline with six stages, each a CLI command (`python -m xsell <stage>`), run in order by
`python -m xsell all`:

| Stage | What it does | Main output |
|---|---|---|
| fetch | Kaggle download, streamed zip to Parquet, validation | `data/cache/` + `manifest.json` |
| warehouse | Staging table and star schema in DuckDB | `data/warehouse.duckdb` |
| quality | Eight checks and three profile tables | `reports/data_quality.md` |
| analyze | Events, penetration, transitions, ladder funnel, time to next product, cohorts, engagement, value proxy | `reports/customer_analytics.md`, `reports/analysis/*.csv`, `reports/ladder_proposal.md` |
| performance | Four timed query pairs with `EXPLAIN ANALYZE` plans | `reports/performance.md` |
| train | Feature table, model selection, calibration, evaluation | `reports/model_report.{md,json}`, `artifacts/propensity_model.joblib` |

Principles: SQL lives in `.sql` files and DuckDB does the computing; Python orchestrates, adds
statistics and writes reports; only aggregates and the sampled model dataset reach pandas. Every
path, month, product code, threshold and assumption comes from `config/config.yaml` or
`config/products.yaml`, validated on load with errors that name the setting. There is no API or
web service; the natural deployment is a scheduled batch job writing scores to a CRM table.

## 3. Loading the data

The fetch stage (`src/xsell/data/`):

1. Checks that a Kaggle credential source exists before importing the Kaggle client (the client
   otherwise authenticates at import time and prints its own help), then downloads only
   `train_ver2.csv.zip`. HTTP 401, 403 and 404 get specific messages; 403 points to the
   competition rules page.
2. Streams the CSV out of the zip with `pyarrow.csv.open_csv` in 4 MB blocks, splits each block by
   snapshot month and writes zstd Parquet in row groups of up to 100,000 rows to
   `data/cache/holdings/month=YYYY-MM/`. The uncompressed CSV is never written to disk.
3. Keeps raw attribute text unchanged (cleaning belongs to the visible, tested SQL layer); only the
   customer id, the snapshot date and the 24 flags are typed.
4. Validates: an independent newline count of the CSV must equal the rows the parser read, the
   months must match the config, and the Parquet is read back for row and customer counts.
   Output goes to a temporary folder and is renamed only after it passes.
5. Writes `manifest.json` (sizes, SHA-256 of the zip, counts, peak memory) and deletes the zip.
   A rerun with a matching manifest does nothing.

On the real file this took 171 s, produced 182.5 MB of Parquet and peaked at 635 MB of memory.

## 4. Warehouse

| Table | Grain | Notes |
|---|---|---|
| `stg_holdings` | customer x month | typed, English names, flags with NULL counted then set to 0 |
| `dim_customer` | customer | join date and month, first and last month seen, latest non-NULL segment, sex, province, channel, income; age at first sighting |
| `dim_product` | product | name, family, ladder step from `products.yaml` |
| `dim_month` | month | index 0 to 16, label, customers present |
| `fact_monthly_holdings` | customer x month | 24 TINYINT flags, `n_products`, activity, seniority, segment, relation type, new-customer flag |

The fact table stays wide. A long customer x month x product table would have 24 times as many
rows (about 327 million), most of them zeros. Events are derived from the wide table in one window
pass, and only rows where a flag changed are turned into long form. DuckDB's `COLUMNS()`
expressions let the SQL handle all 24 flags without listing them.

## 5. Data quality

Each file in `sql/quality/` returns the rows that violate it and declares its severity in a header
comment. Critical failures stop the pipeline after the report is written. On the real data
(`reports/data_quality.md`):

| Check | Severity | Result |
|---|---|---|
| Duplicate customer-month | critical | 0 |
| Product flag not 0 or 1 | critical | 0 |
| Star schema row counts reconcile with staging | critical | pass |
| Age outside 0 to 110 | warning | 760 rows |
| Income negative or above 10M EUR | warning | 1,123 rows |
| Customers with a month gap | warning | 8,018 customers |
| Rows with NULL flags filled with 0 | warning | 16,063 rows |
| Customers with no join date | warning | 7,031 customers |

After cleaning, income is NULL in 20.5% of rows (2,794,375), which is why the model has an
`income_missing` flag.

## 6. Product events

`sql/analysis/10_product_events.sql` computes, for every customer and month, the difference
between each flag and the same flag in the customer's previous row, in a single `LAG` window over
`PARTITION BY customer_id ORDER BY month_index`. An adoption is 0 to 1 and an attrition 1 to 0,
counted only when the previous row is exactly one month earlier. Changes across a gap go to a
separate table and are reported, never counted (2,369 on the real data).

**What the real data showed:** 561,710 adoptions and 533,228 attritions, numbers that are close
because many products switch off and on. The first ladder proposal was built from raw transitions
and was dominated by self-transitions, a product followed by the same product. Every adoption
is now marked first-time or repeat: repeat means the customer dropped the same product earlier in
the window. Because holding a product earlier but not in the previous month implies a drop, the rule
is exact. 290,392 adoptions (51.7%) are repeats; for direct debit 92,993 of 153,146 and for credit
card 46,473 of 69,118. Transitions and time to next product use first-time adoptions only.

## 7. Customer analytics

All rates carry 95% Wilson intervals in the reports (`reports/customer_analytics.md`,
`reports/analysis/`). Comparisons are descriptive and correlational.

**Penetration, May 2016:** current account 60.3%, direct debit 12.1%, particular account 10.8%,
e-account 8.1%, payroll account 7.8%, credit card 3.7%.

**Transitions** (first-time adoptions): pension payments to payroll account (6,438 customers) and
payroll to payroll account (6,226), both a median of 1 month apart, then current account to direct
debit (3,893, median 2 months). Payroll account, payroll and pension payments are adopted almost
together, so the confirmed ladder treats them as one step.

**Ladder funnel** (confirmed ladder: current account, direct debit, payroll package, credit card;
a step is reached in or after the month the previous one was reached):

| Step | Reached | Conversion from previous step | Share of all customers |
|---|---|---|---|
| Current account | 622,371 | 65.1% | 65.1% |
| Direct debit | 115,630 | 18.6% | 12.1% |
| Payroll package | 25,496 | 22.0% | 2.7% |
| Credit card | 8,072 | 31.7% | 0.8% |

The current account to direct debit step converts 35.0% for top-tier customers, 26.5% for
individuals and 8.6% for university customers; by joining channel, about 29% for KAT and KFC
against 6.9% for KHE and 3.1% for KHQ (`reports/analysis/13_ladder_funnel.csv`).

**Time to next product:** 160,441 customers (16.8%) made at least one first-time adoption in the
window; the median time from first observed snapshot to that adoption is 3 months, and 33.1% did so
after one month. Customers already present in January 2015 had history before the window, so this
is time since observation started.

**Engagement:** the active share fell from 53.2% in January 2015 to 42.5% in May 2016. In May 2016
it was 98.9% for top-tier, 48.2% for individuals and 28.1% for university customers, and 0.7%,
37.5%, 84.3% and 98.8% for customers with zero, one, two and three products.

**Join cohorts:** the 2015-01 to 2015-05 cohorts held 66.0% to 70.7% of customers with a product 12
months after joining. The July to October 2015 cohorts (14,449 to 28,121 customers) are several
times larger than the cohorts before them (3,256 to 4,293); the data does not explain why.

**Value proxy:** in May 2016, 25.2% of present customers held no product, 54.1% held one product
family, 12.7% two and 8.0% three or more. Income is missing for 24.6% of them.

## 8. Query performance

Four pairs in `sql/performance/`, each answering one question two ways (a common baseline and a
candidate optimisation), with identical results checked by the tests. Each variant ran once to warm
up and then five timed runs; the table shows medians (`reports/performance.md`, plans in
`reports/performance/plans/`):

| Pair | Baseline (s) | Candidate (s) | Faster |
|---|---|---|---|
| Adoption events: self-join vs `LAG` window | 2.800 | 5.776 | baseline, 2.1x |
| Monthly snapshot: load then filter vs partition pruning and projection | 47.582 | 0.034 | candidate, 1,397x |
| Customer aggregates: recompute vs materialised table | 6.735 | 0.010 | candidate, 654x (build 5.9 s, pays back after 0.9 queries) |
| Running count per customer: range self-join vs cumulative window | 44.884 | 5.042 | candidate, 8.9x |

Why: partition pruning opens one of 17 monthly folders and projection reads 2 of 48 columns; the
materialised table has one row per customer instead of one per customer-month; the range join
produces n(n+1)/2 rows per customer for n months before summing them, while the cumulative window
sorts once and keeps a running total.

The first pair went the other way from row-store intuition. For an equality lookup (this month
against the previous month) DuckDB's parallel hash join is cheaper than the window operator, which
must sort every row by customer and month. The analysis keeps `LAG` because the same pass also finds the
previous row across a gap, which the exact month-minus-one join cannot see. The lesson: measure
rather than assume, and know which shape of problem windows are good at (cumulative and ranked
calculations).

## 9. Propensity model

**Target:** a customer who does not hold the credit card in month t holds it in t+1. The training
base rate (0.58%) is above the 0.2% floor, so the fallback target "any new product" was not used.

**Features** (`sql/features/20_propensity_features.sql`), all from months up to t: the 23 other
product flags, product count and its 1- and 3-month change, months since first observed, seniority,
adoptions and attritions in the last 3 months, active months in the last 3, activity, new-customer
flag, segment, relation type, age band, sex, joining channel (top 10 plus other) and log income
with a missing flag.

**Split and sample:** train on feature months 2015-04 to 2015-12, validate on 2016-01 to 2016-02,
test on 2016-03 to 2016-04 (labels from the following month), no shuffling. A deterministic 20%
customer sample (integer hash of the customer id) gave 1,360,046 training rows with 7,852 adopters,
352,758 validation rows and 356,058 test rows.

**Leakage guards:** features come only from months up to t; tests check that feature months precede
label months, that the target's own flag and the labels are not features, that changing every value
after month t leaves all features at or before t unchanged (with a control showing the comparison
does detect a change at t), and that preprocessing is fitted on training rows only.

**Selection and calibration** (validation PR-AUC): XGBoost 0.1628, logistic regression 0.0931,
rule baseline 0.0195, base rate 0.0048. XGBoost was selected. Both models are class-weighted, which
inflates raw probabilities; sigmoid calibration on validation moved the Brier score from 0.0791 to
0.0044, and in the test calibration table the top bin predicted 4.18% against 4.06% observed.

**Test results** (scored once; 95% intervals from 1,000 customer-level bootstrap resamples):

| Measure | Estimate | 95% CI |
|---|---|---|
| ROC-AUC | 0.956 | 0.953 to 0.959 |
| PR-AUC | 0.166 | 0.151 to 0.184 |
| Brier score | 0.0044 | 0.0042 to 0.0046 |
| Share of adopters in top 5% / 10% / 20% | 73.5% / 85.5% / 95.6% | top 10%: 83.9% to 87.2% |
| Top-decile lift | 8.55x | 8.39x to 8.72x |

PR-AUC was 0.180 and 0.153 in the two test months, so performance held across them. Baselines on
test: base rate 0.0047, rule 0.0167.

**First-time adoption versus re-adoption.** 85% of test adopters had held the card in an earlier
month. Splitting the same scores:

| Group | Rows | Adopters | Base rate | ROC-AUC | PR-AUC | Adopters in top 10% |
|---|---|---|---|---|---|---|
| Never held the card before t | 346,818 | 252 | 0.07% | 0.901 | 0.006 | 63.1% |
| Held it earlier | 9,240 | 1,436 | 15.5% | 0.678 | 0.285 | 21.0% |

The headline numbers are carried by re-adoptions, a card switching back on, which is easy to
predict from recent history (`attritions_last_3m` and product-count changes are among the top
permutation importances). Genuine first-time adopters are still ranked well (6.3x lift in the top
decile) but are rare, so precision stays low. This is not leakage, since every input is from month t
or earlier, but it changes what the model is good for.

**Interpretation:** permutation importance on 50,000 validation rows ranks relation type, product
count, attritions in the last 3 months, the 1-month product-count change and active months highest.
The logistic regression odds ratios are dominated by sparse categories (single joining channels,
relation types) and are a weak guide.

**Contact capacity:** contacting the top 10% of test rows (35,606) reaches 1,444 adopters, against
1,487 expected from the calibrated probabilities. The model report converts this to value with an
assumed 100 EUR margin and 1 EUR contact cost; those are assumptions, and the adopters include
customers who would have adopted anyway.

## 10. Testing

121 tests, run by GitHub Actions on Ubuntu with Python 3.12 on every push (never touching Kaggle):

- **Two synthetic datasets in the raw Kaggle format.** A 60-customer fixture with hand-counted
  answers (planted adoptions, attritions, a repeat adoption, a month gap, missing income, a
  `-999999` seniority, mixed codes, an impossible age, missing join date, join cohorts, inactive
  customers). A seeded 2,000-customer fixture with a learnable credit card signal for the model.
- **Unit and integration tests** for configuration errors, conversion (including corrupt zips,
  missing members, wrong headers, embedded line breaks), missing credentials and HTTP errors, every
  quality check, every analysis query, the ladder funnel, identical results for every performance
  pair, leakage, the fast bootstrap metrics against scikit-learn, training determinism and the
  target fallback.
- **End-to-end:** `python -m xsell all` through the CLI in a temporary project, plus the error
  paths (invalid config, missing inputs, missing credentials, stopping at the first failure).

## 11. Design decisions

| Decision | Rationale |
|---|---|
| DuckDB on a laptop | Columnar, parallel and fast on 13.6M rows without a server; reads Parquet directly |
| Stream zip to month-partitioned Parquet | Never stores the uncompressed CSV; month partitions enable pruning; memory stays flat |
| Wide fact table | 24 times fewer rows than a long table; events need only one window pass |
| SQL in files, parameters bound by name | Reviewable SQL; no string-built queries for values |
| Severity in each quality check's header | Adding a check means adding one file |
| First-time vs repeat adoptions | The real data showed half of adoptions are products switching back on |
| Ladder confirmed by a person | The greedy proposal follows the data, but bundling the payroll products is a judgement |
| PR-AUC for selection | Positives are rare; a no-skill model scores the base rate |
| Time-based split, test used once | Matches how the model would be used; avoids optimistic estimates |
| Customer-level bootstrap | One customer contributes rows in several months, so rows are not independent |
| Calibration on validation | Class weighting distorts probabilities; the capacity table needs real ones |
| Report performance results as measured | The self-join beat the window on DuckDB; hiding that would misstate the evidence |

## 12. Limitations and future work

Limitations: no revenue data (value is a proxy and money figures are assumptions); propensity is
not uplift; only 17 months of a Spanish bank in 2015 to 2016; a 20% customer sample for training;
the ladder simplifies real journeys; product flags switch off and on, so raw adoption counts
overstate new sales; cohort and segment comparisons are correlational.

Future work: a randomised targeting test to measure incremental adoption; a model trained only on
first-time adoption (its base rate is about 0.07%, so it needs the full customer base rather than a
20% sample); uplift modelling once experiment data exists; survival analysis for time to next
product; a scheduled monthly refresh with drift monitoring (population stability index).

## 13. Reproducing the results

Machine used (`reports/pipeline_run.md`): AMD Ryzen 5 5500U, 12 logical cores, 15.3 GB RAM,
Windows 11, Python 3.12.12, DuckDB 1.5.6 limited to 4 GB and 10 threads. Full run: 1,583 s (fetch
171, warehouse 79, quality 7, analyze 15, performance 1,044, train 267), peak process memory 4,249
MB. The query timings in section 8 come from a later rerun of the performance stage
(`reports/performance.md`).

```bash
pip install -r requirements-dev.txt -e .
python -m xsell all
```

Training is deterministic (seed 42): rerunning gives the same model report apart from its time and
commit stamp. Setup, configuration and common errors are covered in the README and
`PROJECT_INSTRUCTIONS.md`.
